# fxkit 双模型复核模式

这条流程适用时（方案、架构判断、排障定论、代码审查、公开 API 改动），结论文件落盘之前，禁止派子代理去做「读代码并下判断」。

## 第 1 步：当前模型自己做判断

自己读代码、自己下结论。这一步不许派 `reviewer`、`explore`、`generalPurpose` 去做这个判断。

判断标准：子代理的输出如果会变成结论的内容，就是在代替第 1 步。和这次判断无关的搜索可以派，例如用户只问某个符号在哪。「先扫几个包再汇总」属于代替第 1 步，不能改口叫无关搜索。

## 第 2 步：结论落成文件

结论不能只活在对话里，因为它进不了子代理的上下文。

- **方案 / 判断类** → 写进 `.cursor/plans/<主题>.plan.md`
- **代码改动类** → 确认改动已在工作区，并在同一份文件里写清改了什么、为什么

文件必须自包含：判断、依据、哪些是故意的取舍。
涉及现有代码的每条判断要有文件路径和行号；没有位置的句子不算依据。纯方案取舍写清选择和理由即可。
不要写「请复核这个仓库」这种没有判断的任务书。

跳过这步，第 3 步必然失败：reviewer 会直接拒绝。

## 第 3 步：文件落盘之后再派复核

只派 `reviewer` 这一个子代理。

写文件和派发不要放在同一次并行工具调用里。文件还没写完时 reviewer 读不到，会按输入不完整拒绝。

传参要求：

- 把结论文件路径原样交过去。绝对不要写「复核上面的结论」——它看不到本对话。
- 说清复核范围：复核哪几个判断、涉及哪些文件、哪些是**故意为之**的取舍（避免它把设计选择当 bug 报）。
- 碰到公开 API 改动时，明确告知这是库的对外契约，让 reviewer 按兼容性那一类重点查。

## 第 4 步：按复核结果收敛

| 复核返回 | 你的动作 |
|---|---|
| `可执行` | 明说「复核通过」，附带它指出的可选项 |
| `需修正后再执行` | 先修阻塞项和应修项，再给最终结论 |
| `方案不成立，需重做` | 重做。不要辩解，也不要只改表面措辞 |
| `调用方还没有自己的结论，拒绝代做判断。` | 不要当成通过，也不要换个说法再派一次。回到第 1 步，把判断和依据写进文件，然后再派 |

复核意见要**逐条**回应，不要合并成「基本没问题」。

你和 reviewer 有分歧时，把分歧点、它的理由、你的理由一起摆出来，交给用户裁决——不要自己单方面判定它对或你对。

## 反模式（出现即视为没执行本模式）

- 开工第一件事就是派子代理，自己还没读完、还没写结论
- 用 `explore` 或其他子代理代替自己的判断，再把汇总交给 reviewer
- 同一次并行工具调用里又写结论又派 reviewer
- 自己复核自己：用同一个模型、同一段上下文重看一遍，然后说「已复核」
- 因为「感觉没问题」「改动很小」跳过第 3 步
- 把 reviewer 的八条意见归纳成两句「建议关注边界情况」
- 只在用户明确说「复核一下」时才调 reviewer
